# 叙事模式库

案例叙事不按模板填空，按项目实质选择模式。判断依据：这个项目的价值主要是在哪个环节产生的？

## 模式一：问题驱动型

**适用**：项目的价值在于发现并定义了一个被忽视的问题，而不只是执行了一个需求。

**识别信号**：需求文档之外的用户抱怨、数据异常、客服工单、被长期搁置的已知问题。

**骨架**：

1. 表象与真问题：大家看到的是什么，实际问题是什么。
2. 为什么之前没人解决：成本、归属、认知盲区——这解释了机会为什么留给了你。
3. 问题定义的验证：用什么证据确认这不是伪需求。
4. 方案与关键取舍。
5. 结果：问题定义本身带来的方向改变，比视觉产出更重要。

**常见翻车**：把"老板提的需求"包装成"我发现的问题"。检验方法——如果换个设计师接手，问题定义会一样吗？会，则你不是问题的发现者，叙事要降级为执行视角。

## 模式二：系统构建型

**适用**：价值在于从混乱中建立秩序：设计系统、组件库、协作流程、规范、方法论沉淀。

**识别信号**：重复劳动、多人协作不一致、交付质量波动、新成员上手慢。

**骨架**：

1. 混乱的代价：用具体数字或事件说明混乱的成本（返工率、交付周期、口径分歧）。
2. 秩序的设计原则：不是"建了一个组件库"，而是"基于什么原则决定哪些该抽象、哪些不该"。
3. 推广与采纳：系统没人用等于没建。如何推动采纳是这类案例的核心章节。
4. 秩序的收益：采纳率、交付效率、质量一致性变化。

**常见翻车**：只展示组件库的成品截图。系统型案例的说服力在"采纳"和"收益"，不在组件数量。

## 模式三：验证迭代型

**适用**：价值在于认知闭环：提出假设、设计验证、被数据打脸、修正方向。

**识别信号**：A/B 实验、可用性测试推翻初稿、上线后数据与预期不符、多轮方向调整。

**骨架**：

1. 初始假设与其依据：当时为什么相信这个方向。
2. 验证设计：用什么方法、什么指标判断对错。
3. 认知被修正的时刻：这是全案例最重要的一段，详细写。
4. 修正后的方案与最终结果。
5. 方法论沉淀：这次验证改变了你之后的什么工作方式。

**常见翻车**：只写成功的迭代，隐藏被打脸的轮次。被推翻又修正的弧线恰恰是这类案例的可信度来源。

## 模式四：0→1 探索型

**适用**：价值在于在高度不确定中定义问题本身：新产品、新市场、新业务线。

**识别信号**：没有现成需求文档、目标用户未被验证、竞品参照物缺失、资源与方向同时受限。

**骨架**：

1. 不确定性的具体形态：不清楚用户是谁，还是不清楚场景，还是不清楚商业模式？分开说。
2. 降低不确定性的路径选择：先验证什么、为什么是这个顺序。
3. 关键转折点：哪个发现改变了产品方向。
4. 从探索到收敛：如何把一个开放问题变成可执行的方案。
5. 结果与未解决的问题：0→1 允许有遗留问题，诚实标注比假装圆满更可信。

**常见翻车**：把 0→1 写成线性成功史。真实的探索充满死胡同，至少保留一条走不通的路。

## 模式选择决策表

| 项目实质 | 首选模式 | 信号词 |
|---|---|---|
| 发现并定义了新问题 | 问题驱动型 | 洞察、盲区、重新定义 |
| 建立系统/规范/流程 | 系统构建型 | 一致性、效率、规模化 |
| 假设驱动的多轮迭代 | 验证迭代型 | 实验、数据、修正 |
| 新业务/新市场探索 | 0→1 探索型 | 不确定、定义、从哪开始 |

一个项目可能横跨多种模式。选**价值密度最高**的那一段作为主叙事，其余压缩为背景。两个案例不得使用同一叙事模式交付——面试官会察觉模板感。
